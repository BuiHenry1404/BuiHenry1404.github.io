AgentBox: AI agent cho quy trình phát triển phần mềm

AgentBox Ecosystem · FPT Software · 04/2026 – nay

AgentBox chạy các nhóm AI agent xuyên suốt quy trình phát triển phần mềm. Tôi làm bốn phần: các agent SDLC và workflow tài liệu của chúng, phần chọn model theo từng agent và lớp LLM provider, Azure DevOps service phía sau Digital Worker System của nhóm, và đưa dự án lên nền tảng với vai trò Forward Deployed Engineer.

Phần 1 — 6 agent SDLC chuyên trách và workflow 9 bước

Workflow nhận một ý tưởng sản phẩm còn sơ khai rồi viết ra yêu cầu, đặc tả, thiết kế và mockup giao diện. Khi tôi nhận phần này, chỉ khoảng một nửa số lần chạy cho ra tài liệu dùng được ngay. Lỗi nằm ở workflow chứ không ở model: có bước viết văn tự do trong khi bước sau cần một file, có bước bỏ qua đầu ra vì chưa ai đánh dấu là bắt buộc.

Tôi dựng lại thành 9 bước, mỗi bước một đầu ra xác định:

brainstorming → PRD nháp → PRD → SRS → UX flow → kiến trúc (C4) → API & dữ liệu → mockup → ma trận truy vết
  • Bước brainstorming có người duyệt. Agent đầu tiên đặt câu hỏi cho tới khi ý tưởng đủ rõ để viết yêu cầu.
  • Mỗi bước một file. PRD.md, SRS.md và ma trận truy vết được các bước sau bổ sung, nên có thể kiểm tra tự động một bước đã xong chưa.
  • Chạy lại theo từng bước. Bước lỗi được chạy lại (tối đa 2 lần) thay vì bỏ cả lần chạy.
  • Đầu ra truy vết được. Mức ưu tiên MoSCoW và ID cố định đi từ user story tới yêu cầu, thiết kế và mockup, kèm sơ đồ C4, sequence và ERD.

Tôi xây 6 agent chuyên trách trên bộ khung có sẵn: brainstorming, phân tích yêu cầu (Job Stories), kiến trúc kèm kịch bản test BDD, UX, mockup, và review PRD theo kiểu Red Team. Mỗi agent có persona, system prompt, skill và tài liệu tham khảo riêng (ký pháp C4, framework NFR, quy ước SRS, checklist review). Tài liệu tham khảo tốt quan trọng hơn cách viết prompt: agent kiến trúc có ký pháp C4 và framework NFR cụ thể sẽ viết ra bản thiết kế mà kiến trúc sư review được.

Kết quả: ~90% tài liệu từ agent chỉ cần 1 lần review, và các agent giúp 4 dự án lên production nhanh hơn.

Phần 2 — Chọn model theo từng agent và lớp LLM provider

Trước đây mọi bước chạy chung một model mặc định. Model rẻ làm hỏng các bước cần suy luận, model đắt thì phí ở các bước đơn giản. Tôi thiết kế và xây phần chọn model theo từng agent:

  • Mỗi agent chạy trên client model của chính nó. Một lần chạy swarm mở một client cho mỗi deployment được gắn, và mỗi bước chạy trên model của agent đó thay vì model mặc định chung.
  • Một cấu hình, bốn tầng. Lựa chọn model được truyền xuyên Go CLI, ứng dụng desktop, web UI và orchestrator, nên chạy từ đâu cũng dùng đúng model.
  • Mỗi bước ghi lại model đã dùng, để so sánh chi phí và chất lượng theo từng agent.
  • Cấu hình provider an toàn hơn. Credential Azure phải khai báo rõ (không tự lấy ngầm), cấu hình LLM không dùng chung giữa các tài khoản, và một override cũ không còn làm hỏng cả lần chạy.

Kết quả: chi phí LLM mỗi workflow giảm khoảng 45%.

Phần 3 — Azure DevOps service phía sau Digital Worker System

Digital Worker System của nhóm cho phép developer giao task cho AI agent mà không rời Azure DevOps. Trước đây, mọi bước quanh một task đều do developer làm tay:

PM tạo task → dev tạo subtask → dev nhập estimate → dev cập nhật status → dev tìm context, viết code → dev mở PR, cập nhật status

Có Digital Worker System, developer chỉ cần verify:

PM tạo task → @mention → hộp thư + poller → Digital Worker: subtask, estimate, status, code → tạo nhánh, đẩy code, work item qua REST → PR → dev verify

Bản thân Digital Worker là sản phẩm của nhóm. Phần của tôi là Azure DevOps service mà nó chạy trên đó: một ứng dụng FastAPI gồm 64 module và 32 endpoint trên 10 router, xác thực token qua Supabase và Azure DevOps REST client chạy bất đồng bộ.

  • Hộp thư @mention và poller. Mỗi lần mention trên work item được đưa vào một hộp thư, poller đọc lần lượt, chạy cho cả Azure DevOps cloud lẫn Azure DevOps Server tự host. Người dùng on-prem được nhận diện bằng tài khoản Windows, và webhook gửi lại cũng không làm một yêu cầu chạy hai lần.
  • Tool REST cho agent. Agent tạo nhánh, xem trạng thái nhánh, đẩy file và tạo work item (qua JSON-Patch) bằng Azure DevOps REST API.
  • Kết quả gọn gàng trên ticket. Câu trả lời của agent được đăng thành comment dạng markdown, và ký tự @ trong code block không còn bị hiểu là mention.
  • Tự phục hồi. Task bị treo, mất kết nối hay chạy trùng đều được xử lý tự động; access token được che trong log.

Kết quả: developer chỉ cần verify thay vì làm 5–8 bước tay cho mỗi task, và ~80% task của agent trên Azure DevOps chạy xong mà không cần ai theo dõi.

Phần 4 — Đưa dự án lên nền tảng (Forward Deployed Engineer)

Agent chỉ làm tốt khi đọc được đủ context của dự án, mà ở đa số dự án context đó nằm rải rác trên SharePoint, docs trong repo và nhóm chat. Với vai trò Forward Deployed Engineer, tôi đưa 2 dự án lên nền tảng:

  • Context engineering. Chuẩn hóa ~100 tài liệu rời rạc (mỗi dự án khoảng 50) thành Azure DevOps Wiki có cấu trúc, với cây trang và mẫu trang cố định, để mọi agent đọc cùng một context dự án.
  • Triển khai. Deploy nền tảng lên server của từng đội.
  • Đưa vào dùng. Làm cùng từng đội để chọn bước nào giao cho agent, bước nào vẫn cần người duyệt.
