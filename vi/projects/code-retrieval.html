Coding agent nên đọc gì, và tìm nó bằng cách nào

Internal developer platform · FPT Software · 06 – 09/2026

Tìm kiếm code nghe như bài toán đã giải xong, cho tới khi người đi tìm là một LLM. Agent không cần danh sách file, nó cần đúng vài trăm dòng — và mỗi dòng thừa là thêm tiền, thêm độ trễ. Coding agent gọi tới tầng này qua MCP tool.

Bài toán

Coding agent của nền tảng làm việc trên các codebase nội bộ lớn: 15–20 repo được index, lớn nhất là một monorepo 3 triệu dòng. Chất lượng truy xuất quyết định mọi thứ phía sau. Ít ngữ cảnh quá thì agent trả lời về đoạn code nó chưa từng thấy; nhiều quá thì mỗi truy vấn tốn hơn, chậm hơn, mà chưa chắc đúng hơn.

Benchmark

Tôi so ba cách truy xuất trên một bộ truy vấn nội bộ cố định:

  • regex / grep — không index, so khớp văn bản thuần.
  • Đồ thị code (Tree-sitter → Neo4j) — parse code thành đồ thị cấu trúc; truy vấn đi theo quan hệ symbol và lời gọi thật.
  • Embedding search (CodebaseMemory, pgvector) — tìm theo độ tương đồng ngữ nghĩa trên các đoạn code.

Chấm trên ba trục, vì tối ưu riêng một trục nào cũng dẫn tới đáp án sai:

  • Chi phí token — bao nhiêu ngữ cảnh gửi cho model mỗi truy vấn.
  • Độ trễ — agent phải chờ bao lâu.
  • Độ đúng luồng — code trả về có nằm trên đường chạy thật của chương trình không.

Kết quả benchmark

Embedding search thắng ở hai trục dễ đo nhất. Nó trả kết quả nhanh hơn đồ thị nhiều lần và giảm 20–30% ngữ cảnh gửi cho agent so với truy xuất file bằng regex — khoản tiết kiệm trên từng truy vấn, cộng dồn rất nhanh ở quy mô 3 triệu dòng.

Nhưng với bài toán bug fix thật thì nó kém hơn. Truy xuất theo ngữ nghĩa lệch khỏi luồng điều khiển thật của chương trình: nó trả về đoạn code đọc giống câu trả lời đúng, chứ không phải đoạn code chạy trên đường có bug. Đồ thị thì vẫn chính xác ở đó, vì nó đi theo cấu trúc chứ không theo độ giống. Nếu chỉ benchmark tốc độ, kết quả sẽ là một chiến thắng gọn gàng — và agent âm thầm kém đi đúng ở việc mọi người cần nhất.

Hybrid retrieval kèm re-ranking

Vì vậy thay vì chọn một phương án thắng, tôi xây hybrid retrieval: regex, đồ thị code và embedding search cùng trả ứng viên, danh sách gộp được re-rank trước khi tới agent. Agent nhận một danh sách ngắn, trong đó code nằm trên đường chạy thật được xếp trước, thay vì nhận kết quả của phương án nào tình cờ trả lời.

truy vấn → regex + đồ thị code + embedding → re-rank → agent (qua MCP)

Với truy vấn bug fix, recall tăng từ ~60% lên ~90% — đoạn code cần sửa giờ nằm trong thứ agent đọc chín trên mười lần. Nhóm chọn hybrid retrieval làm phương án mặc định.

Đo được về sau

Phần bền nhất của việc này là bộ đo. Tôi xây bộ eval cố định cho code search kèm script chấm điểm; chính nó đo ra mức ~60% → ~90%, và mọi thay đổi về sau ở tầng truy xuất đều được chấm trên cùng bộ truy vấn trước khi release. Trước đó, câu hỏi “cái này có tốt hơn không?” được trả lời bởi người vừa thử gần nhất.

Điều này đặc biệt quan trọng với truy xuất, vì thay đổi ở đây khó cảm nhận. Chỉnh cách chia đoạn hay đổi model embedding không tạo khác biệt nào nhìn thấy được, cho tới khi có người gặp đúng trường hợp nó làm hỏng.
