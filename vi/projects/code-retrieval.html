Coding agent nên đọc gì, và cái đó tốn bao nhiêu

Internal developer platform · FPT Software · 06 – 09/2026

Tìm kiếm mã nguồn tưởng như là bài toán đã giải xong, cho tới khi người đi tìm là một LLM. Agent không cần danh sách file, nó cần đúng vài trăm dòng — và mỗi dòng thừa đều là tiền và thời gian chờ. Tôi benchmark ba cách lấy ra đúng vài trăm dòng đó.

Bài toán

Coding agent của nền tảng làm việc trên các codebase nội bộ rất lớn: 15–20 repository được index, trong đó có một monorepo 3 triệu dòng. Chất lượng retrieval quyết định mọi thứ phía sau. Lấy quá ít thì agent trả lời về đoạn mã nó chưa hề đọc; lấy quá nhiều thì mỗi truy vấn vừa tốn tiền vừa chậm, mà chưa chắc đúng hơn.

Nhóm đang dùng code graph dựng bằng Tree-sitter — chính xác, nhưng truy vấn chậm ở quy mô này. Việc của tôi là tìm xem có cách nào phục vụ agent tốt hơn không.

Cách benchmark

Tôi so ba cách lấy context, chạy trên cùng một bộ truy vấn nội bộ cố định:

  • regex / grep — không index gì cả, chỉ khớp chuỗi.
  • code graph Tree-sitter (Neo4j) — parse mã thành đồ thị cấu trúc lưu trong Neo4j, truy vấn đi theo quan hệ symbol và lời gọi thật.
  • embedding search (CodebaseMemory, pgvector) — so độ tương đồng ngữ nghĩa trên mã đã chia chunk.

Chấm trên ba tiêu chí, vì chỉ nhìn một tiêu chí là ra kết luận sai:

  • Độ trễ truy vấn — agent phải chờ bao lâu.
  • Độ đúng luồng — đoạn mã trả về có thật sự nằm trên luồng chạy của chương trình không.
  • Chi phí token — mỗi truy vấn gửi bao nhiêu context cho mô hình.

Kết quả

Embedding search thắng ở hai tiêu chí dễ đo nhất. Nó trả context nhanh hơn code graph nhiều lần, và cắt được 20–30% token context so với cách lấy file bằng regex — tiết kiệm trực tiếp trên từng truy vấn, cộng dồn lại rất đáng kể ở quy mô 3 triệu dòng. Nhóm đưa nó thành cách lấy context mặc định.

Nhưng nó kém hơn ở một điểm. Với việc fix bug trên code thật, embedding search hay trả về đoạn mã trông giống câu trả lời đúng, chứ không phải đoạn mã thật sự nằm trên luồng chạy. Code graph không bị vậy, vì nó đi theo cấu trúc chương trình chứ không theo độ giống nhau về chữ nghĩa.

Điểm này rất dễ bỏ sót, mà bỏ sót thì trả giá đắt. Nếu chỉ đo tốc độ, báo cáo sẽ ghi một chiến thắng rõ ràng, rồi âm thầm làm agent kém đi ở đúng việc người ta cần nó nhất. Nên đề xuất của tôi không phải “bỏ cái này lấy cái kia” mà là dùng kết hợp: code graph cho câu hỏi về phụ thuộc và luồng chạy, embedding cho tra cứu ngữ nghĩa trên diện rộng.

Để về sau còn đo được

Thứ có giá trị lâu dài nhất ở đây không phải lựa chọn cuối cùng, mà là bộ khung đánh giá. Tôi dựng một bộ truy vấn cố định kèm script chấm điểm, nhờ vậy mọi thay đổi về retrieval sau này đều chạy trên cùng bộ truy vấn và cho ra một con số so được. Trước đó, ai vừa thử xong thì người đó kết luận là tốt hay không.

Với retrieval thì điều này càng quan trọng, vì thay đổi ở đây gần như không cảm nhận được. Chỉnh cách chia chunk hay đổi embedding model không làm gì khác đi rõ rệt, cho tới lúc có người gặp đúng trường hợp bị hỏng.
