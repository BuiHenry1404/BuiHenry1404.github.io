xMainframe: hệ multi-agent reverse engineering code mainframe

Legacy PGM – xMainframe · FPT Software · 11/2025 – 04/2026

Hệ multi-agent dùng để reverse engineering code mainframe cũ (COBOL, JCL, CopyBook) và giải thích nó theo ba cấp: từng function, từng file và cả project. Phần khó là bắt các agent trả lời dựa trên code thật, không dựa trên những gì model đoán về COBOL.

Bài toán

Hệ thống mainframe của khách hàng đã chạy hàng chục năm, ít người còn nắm hết. Trước khi sửa, kỹ sư cần biết thay đổi đó ảnh hưởng tới chương trình, job và copybook nào. LLM thông thường trả lời rất tự tin nhưng hay sai, mà trong bảo trì, một phụ thuộc sai khiến kỹ sư sửa nhầm file. Vì vậy mọi thông tin đều phải lấy từ code.

Kiến trúc

COBOL / JCL / CopyBook → parser ANTLR4 → AST → Text Processing Agent → tri thức: Neo4j + pgvector + RAG → Code Processing Agent (LLM) → Coordinator: kiểm tra → báo cáo: function · file · project

1. Parse: từ code thô thành AST

Tôi viết grammar ANTLR4 cho COBOL, JCL và CopyBook, xử lý được cột fixed-format và COPY … REPLACING, rồi duyệt AST bằng visitor để trích program, paragraph, biến và các phụ thuộc CALL / COPY / EXEC ra JSON. File nào cũng parse được: 100% bộ tham chiếu 32 COBOL / 16 JCL và ~3 triệu dòng code nội bộ. Parser mà bỏ qua chỗ không hiểu sẽ để lại lỗ hổng, và đó chính là chỗ agent bắt đầu bịa.

Trước đó, ở Mainframe Studio (08/2024 – 08/2025), tôi đã tối ưu bộ parser này, giảm thời gian parse một codebase lớn từ 1 giờ 30 xuống 45 phút, nhờ tinh gọn rule grammar, chạy codebase lớn bằng Java và chạy parser Python trên runtime C++.

2. Agent và điều phối

  • Text Processing Agent. Làm sạch code, trích artifact từ AST, tạo execution trace (thứ tự PERFORM / CALL giữa các paragraph), chia code theo SECTION và PARAGRAPH, rồi viết prompt cho agent sau.
  • Code Processing Agent (LLM). Giải thích code theo ba cấp: function → file → project. Mọi thông tin thực tế đều lấy qua MCP tool thay vì trả lời theo trí nhớ của model.
  • Coordinator. Lập kế hoạch xử lý, cache kết quả để không giải thích lại một paragraph hai lần, và kiểm tra mọi đầu ra trước khi thành báo cáo.

Tôi làm 7 trong hơn 20 MCP tool của nền tảng: tra phụ thuộc, tính độ dài và vị trí byte của trường CopyBook từ mệnh đề PIC / USAGE, và liên kết giữa chương trình COBOL với job JCL. Bản ghi mainframe có độ dài cố định, lệch một byte là ra một trường khác; tool tính vị trí chính xác (0 lỗi trên các bố cục CopyBook).

3. Tri thức: đồ thị, vector và RAG

  • Knowledge graph Neo4j dựng từ AST: program, copybook, job và quan hệ giữa chúng. Agent lần phụ thuộc trên đồ thị thay vì đọc code thô, nhờ đó số lần tra lại code giảm ~75% và đỡ tốn token.
  • pgvector lưu embedding của code đã parse, để tìm đúng đoạn code theo nghĩa khi câu hỏi không nêu tên chương trình hay biến.
  • RAG trên copybook, JCL và DB schema, với các chunk cắt theo ranh giới SECTION và PARAGRAPH để mỗi chunk luôn là một khối logic trọn vẹn.

4. Đánh giá và báo cáo

Coordinator kiểm tra mỗi phần giải thích bằng validator theo luật, kiểm tra tính nhất quán giữa ba cấp, và điểm tin cậy. Đầu ra gồm báo cáo theo function (JSON + Markdown), theo file, và theo project với sơ đồ luồng vẽ bằng Graphviz / Mermaid từ structured output mà tool trích ra từ AST.

Để đo hallucination, tôi chạy bộ câu hỏi benchmark trên codebase công khai AWS CardDemo và dùng LLM-as-a-judge chấm từng câu trả lời so với mã nguồn. Giám khảo kiểm tra bốn điều: logic code có được mô tả đúng không, mỗi function và paragraph có được giải thích đúng việc nó thật sự làm không, và luồng xử lý có khớp với chương trình không. Tỷ lệ câu trả lời sai ở bất kỳ điểm nào trong số này giảm từ ~50% xuống ~20%.
