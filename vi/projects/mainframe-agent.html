AI agent trả lời từ mã COBOL thật

Legacy PGM – xMainframe · FPT Software · 11/2025 – 04/2026

Trợ lý AI cho kỹ sư bảo trì hệ thống mainframe. Phần khó không nằm ở giao diện chat, mà ở việc bắt agent trả lời dựa trên code thật, chứ không dựa trên những gì mô hình đoán.

Bài toán

Hệ thống mainframe của khách hàng đã chạy hàng chục năm, giờ ít người còn nắm hết. Trước khi sửa, kỹ sư cần biết thay đổi đó ảnh hưởng chương trình nào, job nào chạy chương trình đó, và copybook nào định nghĩa bản ghi liên quan. Tự tìm bằng tay thì phải đọc hàng nghìn dòng nằm rải rác ở nhiều file.

Hỏi một LLM bình thường thì nó trả lời sai mà rất tự tin. Hỏi chương trình này dùng copybook nào, nó đưa ra câu nghe hợp lý nhưng sai. Trong bảo trì, như vậy còn tệ hơn không trả lời: kỹ sư sẽ đi sửa nhầm file. Vì vậy agent không được phép trả lời chỉ bằng trí nhớ của mô hình.

Cách làm: parse code trước, rồi cho mô hình tự tra

Thay vì dán nguyên mã nguồn vào prompt, tôi chuyển codebase thành dữ liệu có cấu trúc, rồi cho mô hình công cụ để tra cứu.

COBOL / JCL / CopyBook → parser ANTLR4 → JSON có cấu trúc → MCP tool → LLM

1. Parser ANTLR4

Tôi xây parser ANTLR4 cho COBOL, JCL và CopyBook. Đầu ra là JSON gồm chương trình, biến, cấu trúc bản ghi và quan hệ phụ thuộc giữa chúng. Yêu cầu đặt ra là file nào cũng phải parse được. Kết quả: parse được 100% bộ tham chiếu 32 file COBOL / 16 file JCL và khoảng 3 triệu dòng code nội bộ.

Code mainframe thật rất khó parse. Câu lệnh phải nằm đúng cột, copybook được chèn thẳng vào code và có thể bị thay nội dung lúc chèn, mỗi nơi lại dùng một biến thể COBOL hơi khác. Parser mà bỏ qua chỗ nó không hiểu thì dữ liệu phụ thuộc sẽ bị thiếu — và agent sẽ bắt đầu bịa đúng ở những chỗ thiếu đó.

Trước đó, ở Mainframe Studio (08/2024 – 08/2025), tôi đã tối ưu bộ parser này: thời gian parse một codebase lớn giảm từ 1 giờ 30 phút xuống 45 phút. Tôi tinh gọn rule grammar, chạy codebase lớn bằng bản Java, và chuyển bản Python sang runtime C++. Nhờ vậy, parse lại 3 triệu dòng thành việc bình thường, không còn phải chạy qua đêm.

2. MCP tool trên dữ liệu đã parse

Tôi phát triển 7 trong hơn 20 MCP tool của nền tảng. LLM gọi các tool này qua tool calling, cho những câu hỏi cần chính xác tuyệt đối:

  • Phụ thuộc — chương trình, job và copybook nào dùng nhau, theo chiều nào.
  • Trường trong CopyBook — độ dài, kiểu dữ liệu và vị trí byte của từng biến trong bản ghi.
  • Quan hệ COBOL – JCL – CopyBook — để câu hỏi về một job được trả lời qua các chương trình mà job đó chạy.

Vị trí trường không được tính gần đúng. Bản ghi mainframe có độ dài cố định, nên một trường được xác định bằng dải byte của nó. Lệch một byte không phải sai nhẹ, mà là ra một trường khác. Tool tính vị trí chính xác, nên câu trả lời của agent về cấu trúc dữ liệu luôn dùng số đúng.

Nguyên tắc: mọi thông tin về codebase đều phải lấy qua tool, và tool đọc từ code đã parse. Mô hình không bao giờ phải tự nhớ COBOL “thường” viết thế nào.

3. Bộ nhớ cho agent

Ban đầu nhóm dùng một thư viện memory có sẵn nhưng không hợp, nên tôi tự xây lớp bộ nhớ. Một câu hỏi như “CUSTOMER-ID ảnh hưởng tới đâu?” được trả lời qua ba bước:

câu hỏi → đồ thị (Neo4j) + tìm theo nghĩa (pgvector) + mã nguồn → LLM trả lời
  • Đồ thị tri thức Neo4j, dựng từ output của parser: chương trình nào đọc trường nào, job nào chạy chương trình nào. Câu hỏi về phụ thuộc được trả lời chính xác ở đây.
  • pgvector để tìm theo nghĩa: embedding trên code mainframe đã parse giúp tìm đúng vùng code, kể cả khi câu hỏi không nêu tên biến hay chương trình.
  • Mã nguồn được lấy sau cùng, để mô hình làm việc trên code thật chứ không phải bản tóm tắt.

Đồ thị thì chính xác nhưng chỉ biết những gì đã được mô hình hoá. Tìm theo nghĩa thì luôn trả về kết quả nhưng có thể sai. Kết hợp cả hai thì chỗ nào trả lời chính xác được sẽ chính xác, chỗ còn lại vẫn có câu trả lời dùng được. Bộ nhớ lưu theo từng dự án và qua nhiều phiên, nên agent không phải tra lại cùng một đoạn code cho câu hỏi sau. Nhờ vậy số lần tra lại code giảm khoảng 75%.

Agent chạy trên LangGraph theo vòng retrieve → reason → tool call → answer, backend viết bằng FastAPI.
