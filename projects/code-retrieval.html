What a coding agent should read, and what that costs

Internal developer platform · FPT Software · Jun – Sep 2026

Code search sounds like a solved problem until an LLM is the one searching. The agent does not want a list of files, it wants the right few hundred lines — and every extra line is money and latency. I benchmarked three ways of finding them.

The problem

The platform's coding agent works over large internal codebases: 15–20 repositories indexed, one of them a 3-million-line monorepo. Retrieval quality decides everything downstream. Too little context and the agent answers about code it never saw; too much and each query costs more and takes longer, without necessarily being more correct.

The team had a Tree-sitter code graph that was precise but slow to query at that scale. The question was whether something else would serve the agent better.

The benchmark

I compared three retrieval strategies on a fixed internal query set:

  • regex / grep — no index, pure text matching.
  • Tree-sitter code graph — parses code into a structural graph; queries follow real symbol and call relationships.
  • Embedding search (CodebaseMemory) — semantic similarity over chunked code.

Scored on three axes, because optimising any one alone gives the wrong answer:

  • Query latency — how long the agent waits.
  • Flow correctness — does the returned code reflect the program's actual control flow.
  • Token cost — how much context is sent to the model per query.

What came out

Embedding search won on the two axes that get measured most easily. It returned context in a fraction of the graph's query time, and cut context tokens sent to the agent by 20–30% compared with regex-based file retrieval — a direct, per-query saving that compounds at 3M-LoC scale. We shipped it as the default retrieval path.

But it was worse at something. On real bug-fix tasks, semantic retrieval drifts from the program's actual control flow — it returns code that reads like the right answer rather than code that is on the execution path. The Tree-sitter graph stays exact there, because it follows structure rather than similarity.

That distinction is easy to miss, and expensive to miss. A speed benchmark alone would have reported a clean win and quietly degraded the agent on exactly the task people care about most. So the recommendation was not "replace one with the other" but hybrid retrieval: the graph for dependency and control-flow questions, embeddings for broad semantic lookup.

Making it measurable afterwards

The most durable part of this work is not the choice, it is the harness. I built a fixed evaluation set plus a scoring script, so any later change to retrieval is compared against the same queries and produces a number. Before that, "is this better?" was answered by whoever had most recently tried it.

That matters for retrieval in particular, because changes here are hard to feel. Tuning a chunking strategy or swapping an embedding model produces no visible difference until somebody hits the case it broke.
