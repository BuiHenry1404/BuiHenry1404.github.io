What a coding agent should read, and how to find it

Internal developer platform · FPT Software · Jun – Sep 2026

Code search sounds like a solved problem until an LLM is the one searching. The agent does not want a list of files, it wants the right few hundred lines — and every extra line is money and latency. Coding agents reach this layer through MCP tools.

The problem

The platform's coding agent works over large internal codebases: 15–20 repositories indexed, the largest a 3-million-line monorepo. Retrieval quality decides everything downstream. Too little context and the agent answers about code it never saw; too much and each query costs more and takes longer, without necessarily being more correct.

The benchmark

I compared three retrieval strategies on a fixed internal query set:

  • regex / grep — no index, pure text matching.
  • Code graph (Tree-sitter → Neo4j) — code parsed into a structural graph; queries follow real symbol and call relationships.
  • Embedding search (CodebaseMemory, pgvector) — semantic similarity over chunked code.

Scored on three axes, because optimising any one alone gives the wrong answer:

  • Token cost — how much context is sent to the model per query.
  • Query latency — how long the agent waits.
  • Flow correctness — does the returned code sit on the program's actual execution path.

What came out

Embedding search won on the two axes that are easiest to measure. It answered in a fraction of the graph's query time and cut the context sent to the agent by 20–30% compared with regex-based file retrieval — a per-query saving that compounds at 3M-line scale.

But on real bug-fix tasks it was worse. Semantic retrieval drifts from the program's actual control flow: it returns code that reads like the right answer rather than code that runs on the path where the bug is. The graph stays exact there, because it follows structure rather than similarity. A speed benchmark alone would have reported a clean win and quietly degraded the agent on exactly the task people care about most.

Hybrid retrieval with re-ranking

So instead of picking a winner, I built hybrid retrieval: regex, the code graph and embedding search each return candidates, and the merged list is re-ranked before it reaches the agent. The agent gets one short list in which code on the real execution path comes first, instead of whichever method happened to answer.

query → regex + code graph + embeddings → re-rank → agent (via MCP)

On bug-fix queries, recall rose from ~60% to ~90% — the right code to change is now in what the agent reads nine times out of ten. The team adopted hybrid retrieval as the default approach.

Making it measurable

The most durable part of this work is the harness. I built a fixed evaluation set for code search plus a scoring script; it is what measured the ~60% → ~90% gain, and every later change to retrieval is scored against the same queries before release. Before that, “is this better?” was answered by whoever had most recently tried it.

That matters for retrieval in particular, because changes here are hard to feel. Tuning a chunking strategy or swapping an embedding model produces no visible difference until somebody hits the case it broke.
