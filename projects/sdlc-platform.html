AgentBox: AI agents for the software development lifecycle

AgentBox Ecosystem · FPT Software · Apr 2026 – present

AgentBox runs groups of AI agents across the software development lifecycle. I worked on three parts: the agents that write project documents, the Azure DevOps integration that lets developers use them without leaving their tools, and helping projects start using the platform.

Part 1 — A document workflow that finishes on the first run

The SDLC workflow takes a rough product idea and turns it into requirements, specifications, design and a UI mockup, with one agent per step. When I took it over, only about half of the runs produced documents that were usable as they came out. The rest were missing a file, or one step produced something the next step could not use, and someone had to notice and run it again.

The failures came from the workflow, not the models. One step wrote free text where the next step expected a specific file. Another skipped an output because nobody had said it was required.

The redesign

I rebuilt the workflow as 9 clear steps:

brainstorming → PRD draft → PRD → SRS → UX flow → architecture (C4) → API & data → mockup → traceability matrix

Three changes made most of the difference:

  • A brainstorming step first, with a human check. A vague idea leads to vague requirements, and every later step gets worse. The first agent asks questions until the idea is specific enough.
  • Each step must produce a specific file. For example PRD.md, SRS.md, and a traceability matrix that later steps extend. Whether a step succeeded can now be checked automatically.
  • Retry only the failed step. If one step fails, only that step runs again. Before, the whole run was thrown away.

I also added diagrams to the specification: story maps, C4, sequence diagrams, ERDs and state diagrams. A diagram is either correct or clearly broken, so it works as a check by itself.

The agents

I built and reworked 6 SDLC agents from an existing base: brainstorming, requirements analysis (Job Stories), architecture with BDD test scenarios, UX design, UI mockup, and Red Team PRD review. For each agent I wrote the persona and system prompt, chose the skills it can use, and added reference material such as C4 notation, NFR frameworks, SRS conventions and review checklists.

Outputs can be traced end to end: MoSCoW priorities and stable IDs carry from a user story to requirements, design and mockup. 4 projects use these agents, and they helped each project reach production faster.

Good reference material mattered more than prompt wording. An architecture agent told to “design a good architecture” writes general advice. Given C4 notation and a concrete NFR framework, it writes a design that an architect can actually review.

Model routing

At first every step used the same default model. Cheap models failed the steps that need deep reasoning, and expensive models were wasted on simple steps. I added model selection per workflow and per agent across four layers — the Go CLI, the desktop app, the Next.js web UI and the Python orchestrator — so each step runs on the model and reasoning level it needs. This cut the cost of a run by about 45%.

Part 2 — Agents inside Azure DevOps

Developers spend their day in Azure DevOps, so the agents should be there too. I built the integration service: a FastAPI application with 64 modules and 32 endpoints across 10 routers, Supabase token auth and an async Azure DevOps REST client.

  • Assign work with @mention. A developer mentions the agent on a work item. The request passes an allow-list check, becomes an agent job, and the result comes back as a comment on the same work item.
  • Turn AI output into tasks. A review report used to mean creating 5–8 work items by hand. A parser now maps each finding to a work item via JSON-Patch, so it takes one click: manual steps went from 5–8 to 1.

Jobs go to workers on developers' machines, which run the agent and report back. Webhooks can send the same mention more than once, so each request runs only once. Long jobs also recover by themselves from hangs, dropped connections and duplicate runs: about 80% of agent jobs finish without anyone watching them.

Some customers need all data to stay inside their own network, so I added support for self-hosted Azure DevOps Server next to the cloud version. Access tokens are masked in logs in both cases.

Part 3 — Onboarding projects (Forward Deployed Engineer)

Agents can only be as good as the project information they can read, and on most projects that information was spread across many files and chats. As a Forward Deployed Engineer, I onboarded 2 projects: I moved their ~100 scattered documents (about 50 each) to Azure DevOps Wiki using a standard page structure and templates, so all agents read the same project context.

Then I worked with each team to bring agent workflows into their daily work: which steps go to an agent, and where a person still has to approve.
