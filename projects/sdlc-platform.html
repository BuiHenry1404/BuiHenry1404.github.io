AgentBox: AI agents for the software development lifecycle

AgentBox Ecosystem · FPT Software · Apr 2026 – present

AgentBox runs groups of AI agents across the software development lifecycle. I worked on four parts: the SDLC agents and their document workflow, per-agent model resolution and the LLM provider layer, the Azure DevOps service behind the team's Digital Worker System, and onboarding projects as a Forward Deployed Engineer.

Part 1 — 6 specialist SDLC agents and a 9-step workflow

The workflow takes a rough product idea and turns it into requirements, specifications, design and a UI mockup. When I took it over, only about half of the runs produced documents that could be used as they came out. The failures came from the workflow, not the models: one step wrote free text where the next step expected a file, another skipped an output nobody had marked as required.

I rebuilt it as 9 steps, each with one defined output:

brainstorming → PRD draft → PRD → SRS → UX flow → architecture (C4) → API & data → mockup → traceability matrix
  • A brainstorming step with a human check. The first agent asks questions until the idea is specific enough to write requirements from.
  • One file per step. PRD.md, SRS.md and a traceability matrix that later steps extend, so whether a step succeeded can be checked automatically.
  • Step-level retries. A failed step runs again (up to 2 retries) instead of the whole run being thrown away.
  • Traceable output. MoSCoW priorities and stable IDs carry from a user story to requirements, design and mockup, with C4, sequence and ERD diagrams along the way.

I built the 6 specialist agents on an existing base: brainstorming, requirements analysis (Job Stories), architecture with BDD test scenarios, UX, mockup, and Red Team PRD review. Each has its own persona, system prompt, skills and reference material (C4 notation, NFR frameworks, SRS conventions, review checklists). Good reference material mattered more than prompt wording: an architecture agent given C4 notation and a concrete NFR framework writes a design an architect can actually review.

Result: ~90% of the documents from the agents need only one review, and the agents helped 4 projects reach production faster.

Part 2 — Per-agent model resolution and the LLM provider layer

Every step used to run on one default model. Cheap models failed the reasoning-heavy steps and expensive models were wasted on simple ones. I designed and built per-agent model selection:

  • Each agent runs on its own model client. A swarm run opens one client per pinned deployment, and every step runs on its agent's model instead of a shared default.
  • One setting, four layers. The model override is passed through the Go CLI, the desktop app, the web UI and the orchestrator, so the same choice holds wherever a run starts.
  • Every step records the model it used, so cost and quality can be compared per agent.
  • Safer provider setup. Azure credentials must be set explicitly (no silent fallback), LLM settings are no longer shared across accounts, and a stale override no longer fails the whole run.

Result: LLM cost per workflow cut by about 45%.

Part 3 — The Azure DevOps service behind the Digital Worker System

The team's Digital Worker System lets a developer hand a task to AI agents without leaving Azure DevOps. Before, a developer did every step around a task by hand:

PM creates task → dev creates subtasks → dev enters estimates → dev updates status → dev finds context, writes code → dev opens PR, updates status

With the Digital Worker System, the developer only verifies:

PM creates task → @mention → mailbox + poller → Digital Worker: subtasks, estimates, status, code → branch, push, work items via REST → PR → dev verifies

The Digital Worker itself is a team build. My part is the Azure DevOps service it runs on: a FastAPI application with 64 modules and 32 endpoints across 10 routers, Supabase token auth and an async Azure DevOps REST client.

  • @mention mailbox and poller. A mention on a work item lands in a mailbox that the poller reads in turn, for both Azure DevOps cloud and self-hosted Azure DevOps Server. On-prem users are identified by their Windows account, and webhook retries never run the same request twice.
  • REST tools for agents. Agents create branches, read branch status, push files and create work items (via JSON-Patch) through the Azure DevOps REST API.
  • Clean results on the ticket. Agent replies are posted as markdown comments, and an @ inside a code block no longer triggers a mention.
  • Recovery. Stuck tasks, dropped connections and duplicate runs are handled automatically; access tokens are masked in logs.

Result: developers only verify, instead of handling 5–8 manual steps per task, and ~80% of agent tasks on Azure DevOps finish without anyone watching.

Part 4 — Onboarding projects (Forward Deployed Engineer)

Agents are only as good as the project context they can read, and on most projects that context was spread across SharePoint, docs inside repos and chats. As a Forward Deployed Engineer I onboarded 2 projects:

  • Context engineering. Standardized ~100 scattered documents (about 50 per project) into a structured Azure DevOps Wiki with a fixed page tree and templates, so every agent reads the same project context.
  • Deployment. Deployed the platform on each team's own servers.
  • Rollout. Worked with each team on which steps go to an agent and where a person still approves.
