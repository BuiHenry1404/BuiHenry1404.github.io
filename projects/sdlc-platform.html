Designing the agents inside an SDLC platform

Internal developer platform · FPT Software · Apr 2026 – present

The platform runs multi-agent "swarms" across the software development lifecycle. I work on two parts of it: the agents that produce the documents, and the Azure DevOps integration that puts them in front of developers without asking anyone to change tools.

Part 1 — Making a document workflow finish

The SDLC swarm takes a rough product idea and walks it through requirements, specification, design and a UI mockup, one agent per stage. When I picked it up, only about half the runs produced documents that could be used as they came out. The other half came out missing a deliverable, or with a stage that produced something the next stage could not consume — and somebody had to notice and run it again.

Failures clustered in a way that pointed at the workflow rather than the models: a stage would produce prose where the next stage expected a named artefact, or would quietly skip an output nobody had specified precisely enough to demand.

The redesign

I rebuilt the workflow as 9 explicit steps:

brainstorming gate → PRD draft → PRD → SRS → UX flow → architecture (C4) → API & data → mockup → traceability matrix

Three changes did most of the work:

  • A brainstorming gate at the front. A vague idea produces vague requirements, and every later stage inherits the vagueness. The first agent's job is to interrogate the idea until there is something specific to specify.
  • A named, structured deliverable per step. Each stage emits a specific artefact — PRD.md, SRS.md, a requirements traceability matrix that later steps extend — so "did this step succeed" became checkable instead of a judgement call.
  • Retry at the step level. When a stage produces an unusable deliverable, that stage re-runs. Previously the whole run was discarded.

I also pushed diagrams into the specification itself — story maps, C4 diagrams, sequence diagrams, ERDs, state diagrams — because a diagram is a structural output an agent either produces correctly or visibly fails to.

The agents

I built and reworked 6 SDLC agents: brainstorming, requirements analysis, architecture, UX design, UI mockup, and adversarial PRD review. For each one that meant a persona and system prompt, the skills it can apply, and reference material that gives it domain footing — C4 notation, NFR frameworks, SRS writing conventions, job stories, adversarial validation checklists.

The agents are now used by 4 projects, which hand them the first pass at brainstorming features and drafting requirements from user stories and use cases.

The reference material mattered more than prompt wording. An architecture agent told to "produce a good architecture" writes generalities. The same agent given C4 syntax and a concrete NFR framework produces something a human architect can argue with — which is the actual goal.

Model routing

Every step originally ran on one global default model. That is wrong in both directions: cheap models fail the reasoning-heavy stages, and expensive models are wasted on mechanical ones. I shipped per-swarm and per-agent model pinning across four layers of the stack — the Go CLI, the desktop app, the Next.js web UI and the Python orchestrator — so each step runs on a model and reasoning-effort setting chosen for that step. That cut the cost of a workflow run by about 45%.

Part 2 — Putting agents where developers already are

An agent platform nobody opens is worth nothing. Developers live in Azure DevOps, so I built the integration service that brings agents to them: a layered FastAPI application of 64 modules and 32 endpoints across 10 routers, with Supabase token auth and an async Azure DevOps REST client.

Two flows matter:

  • Assigning work by @mention. Mentioning the bot on a work item turns the ticket into an agent job behind strict allow-list gates; the answer comes back as a comment on the same work item. The developer never leaves the ticket.
  • Turning AI output into tracked work. A review report used to mean hand-creating 5–8 work items. A parser maps findings onto work items via JSON-Patch, so the same report becomes tracked tasks in one click — roughly 85% less manual effort.

Jobs are dispatched to desktop workers, which claim them, run the agent and report back. Because the same mention can arrive more than once — webhooks retry — the dispatch path is built so a request executes exactly once regardless.

Security and deployment reach

Some customers require that everything stays entirely inside their own infrastructure. I added support for self-hosted Azure DevOps Server alongside the cloud version, so their work items and code references never leave their own network. Credentials are redacted from logs and traces on both paths.
