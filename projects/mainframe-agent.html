xMainframe: a multi-agent system for mainframe reverse engineering

Legacy PGM – xMainframe · FPT Software · Nov 2025 – Apr 2026

A multi-agent system that reverse-engineers legacy mainframe code (COBOL, JCL, CopyBook) and explains it at three levels: each function, each file, and the whole project. The hard part was making the agents answer from the real code, not from what a model guesses COBOL usually looks like.

The problem

The customer's mainframe system is decades old and few people still understand all of it. Before changing anything, an engineer needs to know which programs, jobs and copybooks a change touches. A plain LLM answers that with confidence and is often wrong, and in maintenance work a wrong dependency sends an engineer to change the wrong file. So every fact had to come from the code.

Architecture

COBOL / JCL / CopyBook → ANTLR4 parsers → AST → Text Processing Agent → knowledge: Neo4j + pgvector + RAG → Code Processing Agent (LLM) → Coordinator: verify → reports: function · file · project

1. Parsing: from raw code to an AST

I wrote ANTLR4 grammars for COBOL, JCL and CopyBook that handle fixed-format columns and COPY … REPLACING, then walked the AST with visitors to extract programs, paragraphs, variables and CALL / COPY / EXEC dependencies into JSON. Every file parses: 100% of a 32 COBOL / 16 JCL reference set and of ~3 million lines of internal code. A parser that skipped what it did not understand would leave gaps, and gaps are exactly where an agent starts inventing.

I had already optimized these parsers on Mainframe Studio (Aug 2024 – Aug 2025), cutting parse time for a large codebase from 1h30 to 45 minutes by simplifying grammar rules, running large codebases on Java and the Python parser on a C++ runtime.

2. Agents and orchestration

  • Text Processing Agent. Cleans the code, extracts artifacts from the AST, builds an execution trace (the order of PERFORM / CALL between paragraphs), chunks the code by SECTION and PARAGRAPH, and writes the prompt for the next agent.
  • Code Processing Agent (LLM). Explains the code at three levels: function → file → project. It calls MCP tools for anything factual instead of answering from memory.
  • Coordinator. Plans what to process, caches results so a paragraph is never explained twice, and verifies every output before it becomes a report.

I built 7 of the platform's 20+ MCP tools: dependency lookup, CopyBook field length and byte offset computed from PIC / USAGE clauses, and links between COBOL programs and JCL jobs. Mainframe records are fixed-width, so a field one byte off is a different field; the tools compute offsets exactly (0 errors on the CopyBook layouts).

3. Knowledge: graph, vectors and RAG

  • Neo4j knowledge graph built from the AST: programs, copybooks and jobs and the links between them. The agent traces dependencies on the graph instead of reading raw code, which cut repeated code lookups by ~75% and saved tokens.
  • pgvector embeddings of the parsed code, to find the right code by meaning when a question does not name a program or variable.
  • RAG over copybooks, JCL and the DB schema, on chunks cut along SECTION and PARAGRAPH boundaries so a chunk is always a complete unit of logic.

4. Evaluation and reports

The Coordinator checks each explanation with rule-based validators, consistency checks across the three levels, and a confidence score. Output comes as a function report (JSON + Markdown), a file report, and a project report with flow diagrams drawn in Graphviz / Mermaid from the structured output the tools extract from the AST.
