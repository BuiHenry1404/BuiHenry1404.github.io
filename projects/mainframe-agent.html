Grounding an LLM agent in 50-year-old COBOL

Mainframe modernization · FPT Software · Nov 2025 – Apr 2026

An AI assistant for engineers maintaining mainframe programs. The hard part was never the chat interface — it was making sure the agent answered from the actual code rather than from what a language model assumes COBOL probably looks like.

The problem

The account’s mainframe estate is a body of legacy code that few people still fully understand. An engineer picking up a maintenance request needs to know which programs a change touches, which jobs call them, and which copybooks define the records involved. Answering that by hand means reading thousands of lines across files that reference each other indirectly.

A plain LLM is confidently wrong at this. Ask it which copybook a program depends on and it will produce something plausible, correctly formatted, and not true. For maintenance work that is worse than useless: a wrong dependency answer sends an engineer to change the wrong file. The agent needed to be unable to answer from memory alone.

The approach: parse first, then let the model ask

Rather than feeding raw source into a context window and hoping, I built a pipeline that turns the codebase into queryable structured data, then gave the model tools to query it.

COBOL / JCL / CopyBook → ANTLR4 parsers → structured JSON → MCP tools → LLM

1. ANTLR4 grammars

I wrote grammars for COBOL, JCL and CopyBook that emit JSON: programs, variables, record layouts and the dependency edges between them. The bar I held the parser to was absolute rather than statistical — every file parses, with zero unrecognised constructs, across a 32-COBOL / 16-JCL reference set and roughly 3 million lines of internal code.

Real mainframe source punishes generic parsers. Statements obey IBM fixed-format column rules, copybooks are textually included and can be re-written on inclusion, and the dialect varies by shop. A parser that silently skips what it does not recognise produces a dependency graph with holes in it — and holes are exactly where an agent starts inventing.

2. MCP tools over the parsed data

I developed 7 of the platform's 20+ MCP tools, covering the queries that have to be exact:

  • Dependency extraction — which programs, jobs and copybooks reference each other, and in which direction.
  • CopyBook field analysis — the length, data type and byte offset of every variable in a record layout.
  • Relationship resolution across COBOL ↔ JCL ↔ CopyBook, so a question about a job can be answered in terms of the programs it runs.

Field analysis is the one where approximation is not an option. Mainframe records are fixed-width: a field's meaning is its byte range. Being off by one byte does not produce a slightly wrong answer, it produces a different field. The tools compute offsets exactly, so every downstream answer about record structure inherits that precision rather than the model's guess.

The design principle: the model never sees a question it can answer by recalling what COBOL usually does. Anything factual about this codebase is behind a tool call, and the tool reads parsed source.

3. A memory layer of our own

We started on an off-the-shelf agent-memory library and outgrew it. What this domain needs is not a bag of remembered facts but three different kinds of lookup answered together, so I built the layer myself.

A question like “what does CUSTOMER-ID affect?” fans out into three retrievals before the model writes a word:

question → graph query (Neo4j) + semantic retrieval (Qdrant) + fetch source → LLM synthesis
  • A Neo4j knowledge graph holds the exact structure the parsers produced — which program reads which field, which job runs which program. This is where a dependency question gets an answer that is true rather than plausible.
  • A Qdrant vector store covers the semantic half: finding the relevant area when the question does not name an identifier the graph can key on.
  • The source itself is fetched last, so the model reasons over real code rather than a summary of it.

Splitting it this way matters because the two halves fail differently. Graph traversal is exact but only answers what was modelled; semantic search always returns something but can return the wrong thing. Running both and letting the model synthesise gives an answer that is grounded where precision exists and still useful where it does not. Scoped per project, the layer also keeps what the agent has already looked up, across sessions, so it does not query the same code again for the next question — which cut repeated code lookups by about 75%.

The agent itself runs on LangGraph as a retrieve → reason → tool call → answer loop, with a FastAPI backend.

Results

Read the headline number either way: grounded answers rose from ~50% to ~80%, which is the same as saying unsupported ones fell by about 60%. The agent served 5–6 engineers on the account.

The flow-diagram figure is the honest one to look at. 70–80% is genuinely useful for orientation and genuinely not safe to trust blindly — which is how it was presented to the engineers using it.
