An AI agent that answers from real COBOL code

Legacy PGM – xMainframe · FPT Software · Nov 2025 – Apr 2026

An AI assistant for engineers who maintain mainframe programs. The hard part was not the chat. It was making the agent answer from the real code, not from what the model guesses COBOL usually looks like.

The problem

The customer's mainframe system is decades old, and few people still understand all of it. Before changing anything, an engineer needs to know which programs are affected, which jobs run them and which copybooks define the records. Finding that by hand means reading thousands of lines spread across many files.

A normal LLM gets this wrong with confidence. Ask which copybook a program uses and it gives an answer that looks right but is not. In maintenance work that is worse than no answer: the engineer goes and changes the wrong file. So the agent must not be able to answer from the model's memory alone.

The approach: parse the code first, then let the model look things up

Instead of pasting raw source into the prompt, I turned the codebase into structured data and gave the model tools to query it.

COBOL / JCL / CopyBook → ANTLR4 parsers → structured JSON → MCP tools → LLM

1. ANTLR4 parsers

I built ANTLR4 parsers for COBOL, JCL and CopyBook. They output JSON: programs, variables, record layouts and the dependencies between them. The target was strict: every file must parse. They parse 100% of a 32 COBOL / 16 JCL reference set and of about 3 million lines of internal code.

Real mainframe code is hard to parse. Statements must sit in fixed columns, copybooks are pasted into the code and can be changed while being pasted, and every site uses a slightly different dialect. If a parser skips what it does not understand, the dependency data has gaps — and the agent starts making things up exactly in those gaps.

I had already optimized these parsers on Mainframe Studio (Aug 2024 – Aug 2025): parse time for a large codebase went from 1h30 to 45 minutes. I simplified the grammar rules, ran large codebases on the Java version, and switched the Python version to the C++ runtime. Because of that, re-parsing 3 million lines became a normal step instead of an overnight job.

2. MCP tools on the parsed data

I developed 7 of the platform's 20+ MCP tools. The LLM calls them through tool calling, for questions that must be exact:

  • Dependencies — which programs, jobs and copybooks use each other, and in which direction.
  • CopyBook fields — the length, data type and byte position of each variable in a record.
  • Links between COBOL, JCL and CopyBook — so a question about a job can be answered through the programs it runs.

Field positions cannot be approximate. Mainframe records have a fixed width, so a field is defined by its byte range. One byte off is not a small error — it is a different field. The tools compute positions exactly, so the agent's answers about data layout use correct numbers, not guesses.

The rule: every fact about this codebase comes from a tool call, and the tool reads the parsed code. The model never has to remember how COBOL usually works.

3. Agent memory

We started with a ready-made agent memory library, but it did not fit. So I built the memory layer myself. A question like “what does CUSTOMER-ID affect?” is answered in three steps:

question → graph (Neo4j) + semantic search (pgvector) + source code → LLM answer
  • Neo4j knowledge graph, built from parser output: which program reads which field, which job runs which program. Dependency questions get exact answers here.
  • pgvector for meaning: embeddings of the parsed mainframe code find the right area even when the question does not name a variable or program.
  • The source code is fetched last, so the model works on real code, not a summary.

The graph is exact but only knows what was modelled. Semantic search always returns something, but it can be wrong. Using both gives exact answers where possible and useful answers elsewhere. The memory is kept per project and across sessions, so the agent does not look up the same code again for the next question. That cut repeated code lookups by about 75%.

The agent runs on LangGraph as a loop: retrieve → reason → tool call → answer, with a FastAPI backend.
