A booking agent that cannot invent a booking

Salona Booking · Personal project (2 people) · Aug 2026 · source on GitHub

An AI receptionist for a small nail & hair salon. Customers chat to book; the owner manages availability from an admin UI and a Telegram bot. The interesting constraint is what the model is not allowed to do.

The problem with letting a model book things

A chat booking assistant is a standard demo. It is also a standard way to create a real-world mess: the model confirms a slot that was taken, invents a time that was never offered, or attaches an appointment to the wrong customer. Prompting helps and does not solve it — "never confirm an unavailable slot" is a request, not a guarantee.

For a salon owner this is not an abstract quality metric. It is a customer arriving for an appointment that does not exist.

The design: take away the write tool

The agent runs on LangGraph: a supervisor routes each message to one of three specialist agents (booking, shop info, small talk). The booking agent has seven tools, and none of them can create an appointment.

supervisor → booking / shop / social → guard (no LLM) → customer
customer says yes → confirm (no LLM) → database → phrase (LLM words the reply)

The booking agent can look up shop status, parse a time expression, find free slots, list the customer's appointments and propose a booking or a cancellation — a proposal writes a pending payload with a 10-minute expiry, nothing more. When the customer says yes, a deterministic confirm node with zero LLM calls reads that pending state and writes the appointment from database values. Only then does an LLM word the confirmation, with the date and time handed to it by code; if that call fails, a fixed sentence goes out instead.

Tools return data, not sentences. Every tool answers with JSON — times as an ISO value plus a spoken form, failures as error codes like slot_unavailable — and the prompt decides how to say it. When the tools still returned ready-made Vietnamese sentences, the model copied them: one canned line showed up four times in a single long chat. After the change it did not appear at all.

The customer's identity is bound in a closure when the tools are constructed, so the user id is never an argument the model can influence. Booking for the wrong person is not a low-probability failure — there is no code path that produces it.

The principle: a guardrail that lives in a prompt is a request. A guardrail that lives in the architecture is a guarantee. Where the cost of being wrong is real, the model should propose and deterministic code should commit.

Every reply is checked in code

Some problems would not go away with prompting: the model repeating its own sentence word for word, addressing the same customer two different ways, or writing a time in a format the salon never uses. Rules in capitals and a higher temperature did not fix them. So every reply now passes a guard written in code, with no LLM: three checks, for repeats, form of address and time format. On a violation the LLM gets one rewrite; if the rewrite still fails, the original draft goes out rather than looping.

The repeat check was tuned on 161 sample replies: it flagged 12, with no false positives.

Conversation memory

The chat history sent each turn is capped at 1,500 tokens. But a conversation keeps growing. So what the agent needs to remember is split into three kinds, each handled differently.

1. Current facts — re-read from the database every turn

Who the customer is, how to address them, whether the owner is busy and until when, what appointments they already have. None of this comes from the chat history; it is read straight from the database on every turn. The model cannot remember it wrong, because it is not remembering — it is reading.

Every line here was added after something actually broke:

  • Not stating today's date → the customer says “tomorrow”, the model takes today's date from its training data and books a year out.
  • Not including appointment ids → the model invented an id to cancel, and cancelled nothing.
  • Writing “free in 30 minutes” instead of “free at 3:30” → that sentence stays in the history and is wrong forever after.
  • Not fixing one form of address → the same customer got called two different things four turns apart.

2. The last few turns — kept word for word

This is where the negotiation is happening, so it cannot be compressed. When the customer says “that time works”, you need the previous message to know which time.

3. Older messages from today — a summary plus structured slots

Once the older part passes ~800 tokens, a background pass condenses it into a short summary plus structured slots: what the customer wants to do, the service, the day and time, and the times they already turned down. The LLM fills the slots, then code filters them — a day in the past or a time that has already gone is dropped — and no code path books from them: they only become text in the prompt, and the live context block always wins. Anything already summarised is no longer sent word for word, which is how the chat history stays under 1,500 tokens no matter how long the conversation runs.

The summarising runs in the background, so the customer never waits for it. If it fails three times in a row it stops for the day and falls back to plain history — slower, not broken.

Earlier days are dropped entirely. I did build memory that carried across sessions, then removed it: for salon bookings, yesterday's chat does not help today, and anything that still matters is already in the database.

The owner's side

The salon owner gets a Telegram bot with a four-button keyboard — see today's bookings, see tomorrow's, mark busy, mark free. It contains no LLM at all. For an interface where every action is one of four known operations, a language model would add cost, latency and a failure mode in exchange for nothing.

Every agent run is traced through a self-hosted Langfuse instance, so latency and cost are observable per turn without customer conversations leaving the host. Date and time parsing is isolated into its own LLM call returning structured output, which runs in a measured 2.2–2.4 seconds.
