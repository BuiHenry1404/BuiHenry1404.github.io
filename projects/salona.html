A booking agent that cannot invent a booking

Salona Booking · Personal project (2 people, lead developer) · Aug 2026 – present · source on GitHub

An AI receptionist for a small nail & hair salon: customers chat to ask about the shop, services and prices, and to book or cancel. The interesting constraint is what the model is not allowed to do.

The problem with letting a model book things

A chat booking assistant is a standard demo. It is also a standard way to create a real-world mess: the model confirms a slot that was taken, quotes a price the salon never charges, or says “you're booked” when nothing was written. Prompting helps and does not solve it — “never confirm an unavailable slot” is a request, not a guarantee. For a salon owner it is a customer arriving for an appointment that does not exist.

Architecture: one orchestrator, three sub-agents

The system is built with LangChain + LangGraph. An orchestrator agent reads the customer's message, reasons about the next step and calls three sub-agents as tools — Booking, Shop Info and Services & Pricing — as many times as a turn needs. Sub-agents talk to each other only through the orchestrator: Services reports that a dye job takes two hours, and the orchestrator hands that to Booking.

customer → orchestrator ⇄ Booking · Shop Info · Services → guardrail (code) → customer
  • Sub-agents as tools, not handoffs. I compared the Subagents, Handoffs and Router patterns. Handoffs would let a sub-agent speak to the customer directly; a router keeps no state across a multi-turn chat. With sub-agents as tools, only one agent ever talks to the customer.
  • Stateless sub-agents with structured results. Each sub-agent is rebuilt per call and returns ok, need info or failed plus facts that code extracts from tool output and the database. The orchestrator decides on facts, never on another model's free text.
  • No business tools on the orchestrator. It cannot read the calendar or compute a date itself; every lookup goes through the sub-agent that owns it.

Per-turn context

Each turn starts from a context snapshot built from the database — who the customer is and how to address them, today's date, their upcoming appointments, any proposal waiting for an answer — re-read whenever a tool changes the data. Each sub-agent receives only the part it needs. Tools that cannot be used at that moment are hidden from the model: with a proposal waiting, the orchestrator cannot start another booking until it has dealt with that one.

The first version taught most of these rules. Without today's date, “tomorrow” landed a year out. Without real appointment ids, the model invented one and cancelled nothing — so ids are now an enum built per customer, per turn, and an id the model makes up does not fit the tool's schema. And when tools returned ready-made sentences, the model copied them; tools now return data and the agent decides how to say it.

Human-in-the-loop that fits how people chat

No agent can write a booking. The Booking agent can only create a proposal. The customer approves it on the next turn — with one tap on a button, or by typing a reply, even after asking about something else first — and only then does code commit it.

turn N: proposal + buttons → customer taps or types → turn N+1: one decision path → code writes from DB values
  • One path for every decision. A button press is a plain code API with no model call. A typed reply is labelled by the orchestrator (approve, reject, change, unclear, or not about the proposal), and code may only move that label towards “not yet” — never towards “yes”. Both end in the same decision function.
  • The write takes nothing from the model. Approval checks owner, expiry, that it comes on a later turn, single use and that the slot is unchanged, then writes in one MongoDB transaction together with the turn record, using values from the database rather than anything the model typed.
  • A waiting proposal must be decided. If the turn ends with it still open and the customer did answer, the reply is rejected and rewritten.

I tested LangGraph's built-in pause/resume for this and dropped it. Against the real model it took an off-topic question (“what time do you close?”) as the answer to the paused question; a normal message sent while the graph was paused left a tool call without a result and broke the thread; and the paused question went to the customer without passing the guardrail. Unfinished sub-agent work is instead stored in the database as a waiting session that expires 10 minutes after the last question, and the orchestrator chooses whether to continue it or start something new.

A guardrail inside the agent loop

After every model answer, deterministic evaluators in code check it against the facts from tools and the database before the customer sees anything:

  • Unsupported claims — “booked”, “cancelled” or “moved” with no matching write this turn.
  • Times and prices — every time must be one the tools returned, every amount must sit inside the catalogue's price range for the services involved.
  • Required facts and pending decisions — nothing the turn depended on left out.
  • Form of address and repetition — the same customer is addressed the same way, and the agent does not repeat itself word for word.

A failing answer is removed and gets one rewrite with no tools — text only, same facts, no new lookups or proposals. If that fails too, a code-written fallback goes out. Replies are not streamed, so the customer never sees a wrong sentence that is then replaced.

The principle: a guardrail that lives in a prompt is a request. A guardrail that lives in the architecture is a guarantee. Where being wrong costs something real, the model proposes and deterministic code commits.

Memory and cost

  • Short-term memory per conversation — one thread per customer per day, with LangChain's summarization middleware condensing long histories.
  • Long-term memory per customer — preferences, notes and the last visit, kept in the LangGraph store on MongoDB and consolidated at the start of each new conversation. Sub-agents do not receive it.
  • Bounded cost — per-turn caps on model and tool calls, and an hourly LLM budget per customer that counts sub-agent calls too. Hitting a cap ends the turn with a code-written reply, never a library error message.
  • Observability — every run is traced in a self-hosted Langfuse, so latency and cost are visible per turn without conversations leaving the host.
