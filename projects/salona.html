A booking agent where the AI proposes, the customer approves, and code writes

Salona Booking · Personal project (2 people, lead developer) · Aug 2026 – present · source on GitHub

An AI receptionist for a small nail and hair salon. Customers chat to ask about opening hours, services and prices, and to book or cancel appointments. The key design choice is what the AI is not allowed to do.

Why not let the AI book directly

If the AI can write bookings, it will sooner or later make mistakes: it confirms a time that is already taken, quotes a price the salon does not charge, or says “you're booked” when nothing was saved. Telling it “never do that” in the prompt reduces these mistakes but does not stop them. For the salon owner, the result is a customer showing up for an appointment that does not exist.

Architecture: one orchestrator, three sub-agents

The system is built with LangChain + LangGraph. An orchestrator agent reads the customer's message, decides what to do next and calls three sub-agents as tools: Booking, Shop Info and Services & Pricing. It can call them several times in one turn. Sub-agents only talk to each other through the orchestrator — for example, Services says a hair dye takes two hours, and the orchestrator passes that to Booking.

customer → orchestrator ⇄ Booking · Shop Info · Services → check in code → customer
  • Why sub-agents. I compared three patterns: Subagents, Handoffs and Router. With Handoffs, sub-agents talk to the customer directly. A Router does not remember a conversation across turns. With Subagents, only the orchestrator talks to the customer, which keeps everything under control.
  • Sub-agents return structured results. Each sub-agent keeps no state between calls and returns ok, need info or failed, plus facts that code takes from the tools and the database. The orchestrator decides based on these facts, not on another model's free text.
  • The orchestrator has no business tools. It cannot read the calendar or work out dates by itself. Every lookup goes through the sub-agent responsible for it.

Context for each turn

At the start of each turn, code reads the database and builds the context: who the customer is and how to address them, today's date, their upcoming appointments, and any proposal waiting for an answer. It reads again whenever a tool changes the data. Each sub-agent only gets the part it needs. Tools that cannot be used right now are hidden from the model — for example, while a proposal is waiting, the orchestrator cannot start a new booking.

Most of these rules came from mistakes in the first version. Without today's date, the AI booked “tomorrow” a year ahead. Without real appointment IDs, it made one up and cancelled nothing — so the tool now only accepts IDs from that customer's actual appointments. And when tools returned ready-made sentences, the AI copied them word for word, so tools now return data and the agent writes the reply.

Human-in-the-loop that fits how people chat

No agent can save a booking. The Booking agent can only create a proposal. The customer approves it in the next message — by tapping a button or typing a reply, even after asking about something else first. Only then does code save the booking.

turn N: proposal + buttons → customer taps or types → turn N+1: decision → code saves from database values
  • One path for every decision. A button press is handled by code, with no AI call. For a typed reply, the orchestrator labels it (approve, reject, change, unclear, or unrelated), and code can only make that label more cautious, never turn it into “approve”. Both cases end in the same function.
  • Nothing is taken from the AI when saving. Before saving, code checks that the proposal belongs to this customer, has not expired, comes from an earlier turn, has not been used, and the time is still free. It then saves in one MongoDB transaction, using values from the database.
  • A waiting proposal must be handled. If the customer answered it but the reply leaves it open, the reply is rejected and rewritten.

I tried LangGraph's built-in pause/resume for this and dropped it. In tests with the real model, it treated an off-topic question (“what time do you close?”) as the answer to the paused question. A normal message sent while the graph was paused broke the conversation thread. And the paused question went to the customer without being checked. Instead, unfinished work of a sub-agent is saved in the database as a waiting session that expires after 10 minutes, and the orchestrator decides whether to continue it or start something new.

Checking every reply in code

After each AI answer, rule-based checks in code compare it with the facts from the tools and the database, before the customer sees it:

  • False claims — saying “booked”, “cancelled” or “moved” when nothing was saved this turn.
  • Times and prices — every time must come from the tools, and every price must be within the price range of the services.
  • Missing information — the reply must include the facts the turn depends on and must handle any waiting proposal.
  • Form of address and repetition — the same customer is always addressed the same way, and the agent does not repeat its own sentences.

If a reply fails, the AI gets one chance to rewrite it without tools — same facts, no new lookups. If that also fails, a reply written by code is sent instead. Replies are not streamed, so the customer never sees a wrong sentence that is later replaced.

The principle: instructions in a prompt can still be ignored. A rule in code cannot. When a mistake has real consequences, the AI only proposes, and code makes the change.

Memory and cost

  • Short-term memory — one conversation per customer per day. Long histories are summarized with LangChain's summarization middleware.
  • Long-term memory per customer — preferences, notes and the last visit, stored in the LangGraph store on MongoDB and updated when a new conversation starts. Sub-agents do not see it.
  • Cost limits — a maximum number of model and tool calls per turn, and an hourly LLM budget per customer that includes sub-agent calls. When a limit is hit, the customer gets a reply written by code, not a library error.
  • Monitoring — every run is traced in a self-hosted Langfuse, so speed and cost are visible per turn and conversations stay on our server.
